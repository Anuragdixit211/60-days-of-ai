Lists & Tuples — The Foundations

Ordered collections, mutability, and when to use each

📖 What Are Lists and Tuples?

A list is an ordered, mutable collection of items. A tuple is an ordered, immutable collection. Both can hold mixed types and are indexed starting at 0.

fruits = ["apple", "banana", "cherry"]  # list — mutable
point = (3, 4)                        # tuple — immutable

fruits.append("date")   # works fine
point[0] = 99            # TypeError: 'tuple' object does not support item assignment
Analogy
Think of a list as a whiteboard — you can erase, add, or reorder items anytime. A tuple is like a printed receipt — once issued, the line items are locked in forever. 
nums = [5, 3, 1, 4]
nums.append(2)      # [5,3,1,4,2]
nums.sort()          # [1,2,3,4,5]
nums.reverse()       # [5,4,3,2,1]
nums.pop()           # removes & returns last: 1
nums.remove(4)      # removes first matching value 4
len(nums)          # count of items
letters = ['a','b','c','d','e']
letters[1:3]     # ['b','c']  — start:stop (stop excluded)
letters[:2]      # ['a','b']  — from start
letters[2:]      # ['c','d','e'] — to end
letters[::-1]    # ['e','d','c','b','a'] — reversed
letters[::2]     # ['a','c','e'] — every 2nd item
point = (3, 4)
x, y = point          # x=3, y=4

first, *rest = [1,2,3,4]  # first=1, rest=[2,3,4]

a, b = 1, 2
a, b = b, a      # swap using tuple packing
Common Misconception
"Tuples are just immutable lists, so they're basically the same thing." Not quite — tuples are also semantically used for heterogeneous, fixed-structure data (like a coordinate pair or a database row), while lists represent homogeneous, variable-length sequences. Also: a tuple can contain a mutable object (e.g. a list), so "immutable" only means the tuple's own references can't change — t = ([1,2], 3); t[0].append(9) works fine.
Pitfall: Mutable Default Arguments
def add_item(item, bucket=[]):  # DANGER: default list is created ONCE
    bucket.append(item)
    return bucket

add_item(1)  # [1]
add_item(2)  # [1, 2]  <- unexpected! Same list reused across calls
Fix: use bucket=None and create a new list inside the function if it's None.

🧪 Practical Exercise

Task: Write an expression that returns the last three elements of data = [10,20,30,40,50,60] using slicing.

Key Takeaways
  • Lists are mutable and ordered; tuples are immutable and ordered
  • Slicing uses [start:stop:step], with stop excluded
  • Tuple unpacking is a clean way to assign multiple variables at once
  • Never use a mutable object as a default function argument

Dictionaries & Sets — Key-Based & Unique Collections

Hashing, lookups, and uniqueness

📖 Dictionaries: Key → Value Mappings

A dict stores key-value pairs. Keys must be hashable (immutable-ish: strings, numbers, tuples of immutables). Lookup by key is on average O(1) — constant time — regardless of dict size.

student = {"name": "Riya", "age": 21, "major": "CS"}
student["age"]            # 21 — O(1) lookup
student["gpa"] = 3.8       # add new key
student.get("minor", "N/A")  # safe lookup with default
"major" in student        # True — checks KEYS, not values
Analogy
A dict is like a phone book — you don't scan every entry to find "Riya's number"; you jump straight to it because it's indexed by name. A list, by contrast, is like scanning a sequential guest list from top to bottom.

📖 Sets: Unique, Unordered Collections

A set stores unique, unordered items and supports fast membership testing (O(1) average) plus classic mathematical set operations.

a = {1, 2, 3, 4}
b = {3, 4, 5, 6}

a | b   # union: {1,2,3,4,5,6}
a & b   # intersection: {3,4}
a - b   # difference: {1,2}
a ^ b   # symmetric difference: {1,2,5,6}

seen = set()
seen.add(5); seen.add(5)  # still just {5} — duplicates auto-removed
StructureOrdered?Mutable?Duplicates?Lookup
ListYesYesAllowedO(n) by value
TupleYesNoAllowedO(n) by value
DictInsertion orderYesNo dup keysO(1) by key
SetNoYesNo duplicatesO(1) membership
Common Misconception
"Dicts in Python are unordered." Since Python 3.7, dicts officially preserve insertion order — but you still shouldn't rely on sorted or positional order for logic; use explicit sorting if order matters semantically.
Pitfall: Unhashable Types
bad = {[1,2]: "x"}   # TypeError: unhashable type: 'list'
ok  = {(1,2): "x"}   # fine — tuples are hashable
Lists and sets can't be dict keys or set members because they're mutable — their hash could change, breaking the internal bucket structure.

🧪 Practical Exercise

Task: Given a = {1,2,3} and b = {2,3,4}, write the expression to get elements in a but not in b.

Key Takeaways
  • Dicts map hashable keys to values with average O(1) lookup
  • Sets store unique items and support union/intersection/difference
  • Only hashable (typically immutable) types can be dict keys or set elements
  • Since Python 3.7, dicts preserve insertion order

Comprehensions — Writing Pythonic Code

List, dict, set comprehensions and generator expressions

📖 From Loops to Comprehensions

A comprehension builds a new collection in a single, readable expression instead of a multi-line loop. The general list form is [expression for item in iterable if condition].

squares = []
for n in range(10):
    if n % 2 == 0:
        squares.append(n**2)
# squares = [0, 4, 16, 36, 64]
squares = [n**2 for n in range(10) if n % 2 == 0]
# squares = [0, 4, 16, 36, 64] — same result, one line
Analogy
A manual loop is like giving someone step-by-step directions ("go to the bin, pick it up, check it, put it in the basket, repeat"). A comprehension is handing them the rule directly: "every even number's square, from 0 to 9." Same destination, far less narration.

📖 Dict & Set Comprehensions

# Dict comprehension: {key_expr: value_expr for item in iterable}
word_lengths = {w: len(w) for w in ["cat","elephant","ox"]}
# {'cat': 3, 'elephant': 8, 'ox': 2}

# Set comprehension: {expr for item in iterable}
unique_lengths = {len(w) for w in ["cat","dog","ox"]}
# {3, 2}  — duplicate length 3 collapses to one

# Generator expression: () instead of [] — lazy, memory-efficient
gen = (n**2 for n in range(1000000))  # doesn't build the list in memory

📖 Nested Comprehensions

# Flatten a matrix (list of lists)
matrix = [[1,2,3], [4,5,6]]
flat = [num for row in matrix for num in row]
# [1, 2, 3, 4, 5, 6]  — outer loop first, inner loop second, same order as nested for-loops
Common Misconception
"Comprehensions are always faster and should replace every loop." They're often faster (less overhead, optimized bytecode) but nesting more than 2 levels or cramming complex logic into one line hurts readability. If it needs a comment to explain, a regular loop is usually clearer.
Pitfall: Overusing Side Effects
# Bad — using a comprehension purely for side effects, result discarded
[print(x) for x in range(5)]  # builds a throwaway list of Nones — wasteful

# Good — just use a for loop when you don't need the resulting collection
for x in range(5): print(x)

🧪 Practical Exercise

Task: Write a dict comprehension that maps each number in nums = [1,2,3,4] to its cube.

Key Takeaways
  • List/dict/set comprehensions condense loops into a single readable expression
  • Generator expressions use () and are lazy — great for huge/streaming data
  • Nested comprehensions follow the same order as equivalent nested for-loops
  • Don't force a comprehension when a plain loop is clearer (especially for side effects)

Mastery & Real-World Application

Choosing the right structure, combining them, and performance

📖 Choosing the Right Structure

Real problems rarely say "use a dict." You infer it from the access pattern you need:

  • Need order + duplicates + index access? → List
  • Need a fixed, unchangeable record? → Tuple
  • Need fast lookup by a unique label? → Dict
  • Need to test membership fast, or de-duplicate? → Set
Analogy
Think of these as tools in a toolbox: a list is a numbered filing cabinet drawer (order matters, duplicates fine); a dict is a labeled folder system (grab by label instantly); a set is a bouncer's guest list (only cares "are you on it or not," never lets duplicates in); a tuple is a sealed envelope (contents fixed once sealed).

📖 Combining Structures: Real-World Patterns

# Pattern 1: Grouping data — dict of lists
students_by_grade = {}
for name, grade in [("Amit","A"), ("Riya","B"), ("Zoe","A")]:
    students_by_grade.setdefault(grade, []).append(name)
# {'A': ['Amit', 'Zoe'], 'B': ['Riya']}

# Pattern 2: Counting with a dict comprehension + set of unique items
words = "the cat sat on the mat the cat ran".split()
counts = {w: words.count(w) for w in set(words)}
# {'the': 3, 'cat': 2, 'sat': 1, 'on': 1, 'mat': 1, 'ran': 1}

# Pattern 3: Deduplicating while preserving first-seen order
seen = set()
ordered_unique = []
for x in [3,1,3,2,1,4]:
    if x not in seen:
        seen.add(x)
        ordered_unique.append(x)
# [3, 1, 2, 4]

📖 Performance Intuition

The habit that separates a beginner from a confident Python developer: recognizing that "is X in this collection?" costs very different amounts depending on the container.

OperationListSetDict
x in collectionO(n)O(1) avgO(1) avg (checks keys)
Insert at endO(1) amortizedO(1) avgO(1) avg
Access by position/keyO(1) by indexN/A (unordered)O(1) by key
Common Misconception
"Checking membership with in works the same way on any container." Using in on a 100,000-item list to check membership repeatedly in a loop is a classic hidden performance bug — converting that list to a set first can turn an O(n²) script into an O(n) one.

🧪 Practical Exercise

Task: You have logs = ["error","info","error","warn","info","error"]. Write a dict comprehension that counts occurrences of each unique log level.

Key Takeaways
  • Pick a structure based on access pattern: order/index (list), fixed record (tuple), fast key lookup (dict), fast membership/uniqueness (set)
  • Combining structures (dict of lists, set + list) solves most real grouping/deduplication problems
  • Converting a list to a set before repeated membership checks is a major performance win
  • setdefault and comprehensions eliminate most manual boilerplate

📝 Summary Notes

Lists and tuples give you ordered sequences — mutable vs. immutable. Dicts and sets give you hash-based, near-instant lookups — key-value pairs vs. unique members. Comprehensions let you express "build a new collection from this rule" in one clean line instead of a multi-line loop, and generator expressions extend that idea to lazy, memory-efficient iteration. Mastery comes from matching the structure to the access pattern the problem actually needs — not from memorizing syntax.
